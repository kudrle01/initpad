# ADR-122 — Workspace kapacita je samostatná transakční hranice

**Status:** Accepted

**Kontext.** `TargetAllocation` už omezuje počet prostředí a prostředky na
konkrétním deployment serveru. Nechrání ale sdílený control plane ani object
storage před tím, aby jeden workspace vytvořil neomezený počet projektů,
členů, serverů, souběžných operací nebo build artefaktů. Pouhé
`count` následované zápisem by navíc při dvou API replikách dovolilo, aby oba
požadavky současně obsadily poslední volné místo.

**Rozhodnutí.** Každý `Workspace` uchovává limity projektů, členů,
serverových allocation, aktivních provisioning/deployment operací a
rezervovaných bajtů artefaktů. Platformní administrátor je může měnit v
self-hosted i SaaS edici; členové workspace vidí aktuální využití, ale
politiku nemění.

Kontrola a příslušný databázový zápis probíhají v PostgreSQL transakci s
izolací `Serializable`. Konflikt serializace se omezeně opakuje a po novém
načtení limitu buď uspěje, nebo vrátí `409 Conflict`. Externí SCM operace
mají navíc levnou předběžnou kontrolu; autoritativní je až transakční
kontrola před vytvořením lokálního projektu.

Artefakt rezervuje deklarovanou velikost od stavu `accepted` až po
`available`; failed nebo odstraněný artefakt kapacitu nedrží. Souběžné
operace počítají dohromady provisioning a deployment. Snížení limitu pod
aktuální využití nemaže existující zdroje: zablokuje pouze další práci v
dané kategorii a změna je auditovaná.

**Proč.** Workspace je autorizační i billing/capacity hranice. Jedna centrální
politika se proto dá vysvětlit provozovateli i uživateli a nezaměňuje se s
užším runtime envelope jednotlivého serveru. Serializable transakce chrání
stejný invariant na jedné i více API replikách bez nového distribuovaného
lock manageru.

**Důsledky.** Kapacita je tvrdý admission limit, nikoli metering ani fakturace.
Počítá databázové rezervace, ne skutečnou velikost externího bucketu, a
neprovádí automatické mazání. Nasazení zůstává závislé na existujícím
retention GC a provozním monitoringu. Produkční e-mail, load test a externí
telemetrie jsou samostatné release gates.

**Testování.** Unit testy ověřují všech pět limitů, JSON-safe serializaci
`BigInt`, přesný převod GiB na bajty a audit administrátorské změny. Servisní
regrese dokazují, že create/import, přidání člena, registrace targetu,
spuštění operace i přijetí artefaktu používají transakční claim.
