# ADR-155 — Přejmenování repozitáře nebo účtu nemění identitu projektu ani jeho nasazení

**Status:** Accepted

**Kontext.** Projekt je od ADR-043 identifikován dvojicí poskytovatel a neměnné
ID repozitáře. Vlastník, název, celé jméno a URL jsou jen souřadnice, které se
mohou změnit. Průchod GitHub App na stagingu s releasem 0.2.17 ukázal, že se
tímto rozlišením neřídí zbytek platformy:

- U GitHub projektů se souřadnice po založení nikdy neobnoví. Obnova podle ID
  existuje jen pro Giteu. Po přejmenování repozitáře projekt dál ukazuje
  původní název a čte jen díky přesměrování na straně GitHubu.
- CI callback hledá projekt podle celého jména repozitáře. Workflow po
  přejmenování posílá nové jméno, projekt se nenajde a push se nenasadí.
- Očekávaný tag obrazu se počítá z aktuálních souřadnic projektu. Artefakt
  sestavený před přejmenováním má v archivu tag se starým jménem, artefakt
  sestavený po něm s novým.
- Klíč workloadu se počítá z vlastníka a názvu repozitáře. Tvoří název
  kontejneru na Agentovi i na vestavěném Docker targetu a adresář na SFTP.
  Pouhé přepsání souřadnic by při dalším nasazení založilo druhý workload a
  původní by zůstal běžet bez správy. Platí to už dnes pro Giteu, kde se
  souřadnice obnovují.
- Přejmenování účtu nebo organizace opraví podle ADR-043 jen záznam instalace,
  projekty v ní zůstanou se starým vlastníkem.

Přesměrování navíc není záruka. Jakmile někdo založí nový repozitář se starým
jménem, GitHub přesměrování zruší a uložené souřadnice začnou ukazovat na cizí
repozitář.

**Rozhodnutí.** Identitu nese jen neměnné ID. Všechno, co má přežít
přejmenování, se uloží při vzniku a už se z názvu nepočítá.

1. Projekt dostane uložený klíč workloadu. Nastaví se jednou při založení nebo
   importu stejným výpočtem jako dosud a potom se nemění. Migrace jej všem
   existujícím projektům dopočítá ze současných souřadnic, takže žádný běžící
   kontejner, cesta ani route nezmění jméno. Při založení se ověří, že klíč
   nedrží jiný projekt; obsazená hodnota dostane krátkou příponu z ID
   repozitáře. Agent, vestavěný Docker target, SFTP, diagnostika, odstranění
   nasazení i smazání projektu používají jen tento klíč. Sloupec zůstává
   volitelný, aby do databáze mohl zapisovat i starší obraz: řádek bez
   uložené hodnoty ji odvozuje jako dosud a uloží si ji nejpozději před
   změnou souřadnic.
2. Artefakt dostane uložený odkaz na obraz. Zapíše se při příjmu z ověřeného
   archivu a všechna pozdější nasazení, povýšení, rollback i obnova z object
   store používají jeho hodnotu. Starší artefakty bez uložené hodnoty ji
   odvozují jako dosud; před každou změnou souřadnic se jim ve stejné
   transakci dopočítá z původních souřadnic.
3. Poskytovatel umí vrátit aktuální souřadnice repozitáře podle jeho ID. Pro
   GitHub je to dotaz na repozitář podle ID tokenem instalace. Nahrazuje
   dosavadní dotaz, zda repozitář existuje, takže počet dotazů neroste.
4. Souřadnice projektu se obnoví ve třech situacích: při průběžné kontrole
   projektu, při CI callbacku s neznámým jménem a hromadně v pravidelné
   údržbě poté, co podepsaná událost opravila jméno účtu instalace. Hromadná
   obnova se poskytovatele neptá, protože každý repozitář instalace patří
   jejímu účtu. Obnova zapíše vlastníka, název,
   celé jméno, výchozí větev a URL najednou a zaznamená do auditu původní i
   nové jméno. Když repozitář pod uloženým jménem nemá uložené ID, není to
   chyba čtení, ale důvod dohledat jej podle ID.
5. CI callback, který nenajde projekt podle jména, jej dohledá podle otisku
   svého tokenu. Potom obnoví souřadnice od poskytovatele a callback přijme jen
   tehdy, když se jméno potvrzené poskytovatelem shoduje se jménem v callbacku.
   Jménu z callbacku samotnému platforma nevěří.
6. Název projektu následuje název repozitáře, pokud je nový název platným
   názvem projektu a ve workspace je volný. Jinak projekt svůj název zachová a
   rozhraní ukáže odlišný název repozitáře.
7. URL přidělené spravovanou bránou, CI token, proměnné a secrety projektu se
   přejmenováním nemění.

**Důsledky.** Přejmenovaný repozitář i repozitáře přejmenované organizace se
dál nasazují do stejných kontejnerů a adres. Starý artefakt jde nasadit i po
přejmenování, protože si nese vlastní odkaz na obraz. Název kontejneru po
přejmenování neodpovídá novému názvu repozitáře; je to cena za to, že se
běžící workload nepřesouvá. Změna vyžaduje migraci databáze se dvěma novými
sloupci a zasahuje do všech cest nasazení, proto musí projít podepsanou
aktualizací i živým průchodem. Mezi přejmenováním a první obnovou projekt čte
přes přesměrování poskytovatele jako dosud.

Převod repozitáře na jiného vlastníka mimo dosah instalace se nemění:
poskytovatel jej pro instalaci hlásí jako neexistující a platí dosavadní
úklid projektu. Převod v dosahu jiné autorizované instalace je samostatné
budoucí rozhodnutí.

**Alternativy.** (a) Přejmenování nepodporovat a jen na ně upozornit: malá
změna, ale průchod GitHub App by zůstal nesplněný a přejmenování organizace by
zastavilo všechny její projekty. (b) Přepočítat klíč workloadu a workload
přesunout: vyžaduje řízenou výměnu kontejneru, cesty i route na každém targetu
a při chybě nechává dva workloady. (c) Adresovat všechna volání poskytovatele
podle ID a souřadnice vůbec neukládat: odolnější, ale přepisuje celého
poskytovatele a souřadnice jsou dál potřeba pro zobrazení, klonování a tagy
obrazů. (d) Odebírat událost o přejmenování repozitáře: zrychlí obnovu, ale
vyžaduje změnu registrace App a průběžnou obnovu stejně nenahradí.

**Testování.** Unit testy pokrývají zachování klíče workloadu a nasazení
artefaktu sestaveného před přejmenováním u Agenta, uložení odkazu na obraz při
příjmu artefaktu, obnovu souřadnic podle ID u obou poskytovatelů včetně
odmítnutí odpovědi o jiném repozitáři, přijetí CI callbacku s novým jménem až
po potvrzení poskytovatelem a jeho odmítnutí při neshodě, hromadnou obnovu po
přejmenování účtu, pravidlo pro název projektu a přidělení klíče při kolizi.
Migrační test dokládá, že dopočítaný klíč odpovídá dosavadnímu výpočtu a že
migrace nemění žádné prostředí ani artefakt. Vestavěný Docker target a SFTP
používají stejný klíč jako Agent, vlastní test s přejmenováním nemají.

Naživo rozhodnutí ověřeno není. Ověří se krokem Rename z průchodu GitHub App
pro repozitář i organizaci a podepsanou aktualizací self-hosted instalace s
běžícím workloadem.
