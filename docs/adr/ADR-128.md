# ADR-128 — Artifact ingestion používá vlastní generační execution lease

**Kontext.** Stav `BuildArtifact.ingesting` zabránil druhému callbacku spustit
stejné stažení, ale neurčoval, která API replika práci vlastní. Startup
recovery proto mohl označit zdravé stahování na jiné replice jako selhané a
pozdní worker mohl publikovat nebo smazat objekt novějšího pokusu.

**Rozhodnutí.** GitHub Actions artifact před provider downloadem atomicky
získá krátký databázový lease na `BuildArtifact`. Databázový čas určuje
expiraci, worker lease obnovuje a každý nový claim zvýší
`ingestionGeneration`. Publikace `available` i selhání porovnává ownera a
generaci. Worker po ztrátě fence nesmí měnit databázi ani mazat sdílený
object-store klíč.

Ingestion svázaná s deploymentem současně drží execution lease
`DeploymentOperation` z ADR-126. Následný deploy jej znovu použije ve stejném
async kontextu, takže mezi ověřením artefaktu a publikací prostředí nevzniká
nechráněné okno. Leader recovery ignoruje živý lease a přerušený pokus
ukončí jen generačním compare-and-setem; staré řádky bez lease dostanou
krátkou compatibility grace period. Lehká recovery deployment a artifact
lease běží v každém minutovém leader cyklu, nejen po restartu nebo takeoveru.

**Proč.** Artifact je samostatný trvalý zdroj a může existovat i bez dev
prostředí, proto nestačí pouze lease deployment operace. Oddělený fence
chrání provider download, lokální kontrolu archivu, upload, potvrzení objektu
i načtení image.

**Důsledky.** GitHub artifact ingestion je bezpečná přes restart i souběh API
replik. Přímé synchronní lifecycle mutace a zachycení Gitea OCI image zatím
nejsou touto hranicí pokryty, proto mutační veřejný SaaS stále zůstává
single-replica.

**Testování.** Testy ověřují obnovu pomalého ingestion lease, generační
publikaci, zastavení stale workeru bez mazání sdíleného objektu, ignorování
živého ownera a CAS recovery expirovaného pokusu.
