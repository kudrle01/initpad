# ADR-160 — Vlastní projekty a jejich workflow popisuje manifest a napojují se přes ověřený handoff

**Status:** Proposed

Plán po obhajobě (po MVP). Sleduje epic #119.

**Kontext.** Import existujícího repozitáře (fáze 3) předpokládá, že
1 repozitář odpovídá 1 projektu, 1 image a 1 kontejneru v každém prostředí.
Runtime kontrakt (`port`, `healthPath`, `runtime`) se bere ze šablony, kterou
uživatel při importu vybere. Preflight v `ImportService` vyžaduje `Dockerfile`
v kořeni repozitáře a workflow `ci.yml`, ve kterém hledá řetězce startovního
workflow InitPadu. `Environment` ukazuje na jeden `BuildArtifact` a má jednu
`GatewayRoute`.

Reálný projekt mimo šablony, monorepo `applifting-vsecourse/team-1`, ukázal,
co typický vlastní projekt potřebuje: frontend (nginx) a backend (Nest) ze
společného kořene, routování `/api` na backend pod jednou adresou, Postgres
s trvalými daty, migrace při startu, vlastní CI s testy a frontend, který
zapéká URL backendu při buildu. Zároveň ukázal rizika: tajný klíč předávaný
jako build argument by skončil v artifactu.

Dnešní ověření GitHub artifactu kontroluje repozitář, commit, běh a digest
(`GitHubScmProvider`), ale ne cestu workflow, událost ani větev. Dokud jediný
workflow pochází ze startovní šablony, stačí to. U vlastních workflow by ale
deployovatelný artifact mohl odevzdat kterýkoli workflow repozitáře, například
běh nad neschválenou větví.

Zvažované možnosti:

- Každou složku monorepa importovat jako samostatný projekt. Odmítnuto,
  `Project` je jednoznačně vázaný na repozitář a služby by se povyšovaly
  nezávisle, takže by v testu mohly běžet nekompatibilní verze.
- Spouštět přímo `docker-compose.yml`. Odmítnuto, compose umí volumes, host
  mounty, `privileged`, capabilities a síť hostitele, což by porušilo hranice
  podle `THREAT_MODEL.md` a izolaci allocation (ADR-060). Compose se smí jen
  převést na manifest (bod 9).
- Stavět image v InitPadu místo v CI uživatele. Odmítnuto, platforma by
  spouštěla cizí build se svými credentials a vlastní CI by ztratilo smysl.
- Vlastní omezený manifest, ověřený handoff z vlastního workflow a runtime,
  který si bezpečnostní pravidla vynucuje sám. Zvoleno.

**Bezpečnostní zásady.** Kód, Dockerfile, workflow i manifest projektu jsou
nedůvěryhodné. Důvěra stojí na třech věcech, které projekt ovlivnit nemůže:

1. **Původ artifactu** ověřuje InitPad u SCM provideru, ne podle tvrzení CI.
2. **Oprávnění workloadu** určuje Agent a policy allocation, ne image ani
   manifest. Manifest může jen žádat v mezích policy.
3. **Rozšíření oprávnění** (nová služba, veřejná routa, doména, stavová
   služba, plán, vyšší zdroje) schvaluje člověk s rolí maintainer a výš.

**Rozhodnutí.**

1. **Manifest `initpad.yaml`.** Popisuje služby (`web`, `worker`), routy,
   úlohy, plány, stavové služby a požadované zdroje. Schéma je verzované
   (`version: 1`) a striktní: neznámé klíče jsou chyba, počty, porty, délky a
   zdroje jsou omezené a manifest nemůže určit image stavových služeb,
   volumes, mounty, capabilities, uživatele, síť hostitele ani privilegia.
   InitPad čte manifest **z commitu releasu**, ne z výchozí větve v době
   importu, takže manifest a artifact jsou vždy ze stejného SHA. Šablona se
   stává zdrojem vygenerovaného manifestu s jednou službou; repozitář bez
   manifestu dál používá runtime kontrakt vybrané šablony.

2. **Schvalování změn manifestu.** InitPad ukládá naposledy schválenou
   podobu manifestu. Release, jehož manifest oproti ní rozšiřuje oprávnění,
   se sestaví a ověří, ale nasadit ho lze až po schválení rozdílu maintainerem.
   Rozdíl se ukáže i v produkční žádosti. Zúžení oprávnění schválení
   nepotřebuje. Schválení i zamítnutí se zapisuje do auditu.

3. **Ověřený handoff z vlastního workflow.** InitPad dodá krok
   `initpad/handoff` pro GitHub Actions a Gitea Actions, verzovaný a
   podepsaný v release procesu platformy; dokumentace ho uvádí připnutý na
   commit SHA. Krok odevzdá image služeb jako jeden immutable artifact
   (bundle: OCI archivy a manifest pod jedním digestem) a pošle callback.
   Projekt v InitPadu eviduje **identitu povoleného workflow**: cestu souboru,
   povolené události (`push`, `workflow_dispatch`) a povolené větve (výchozí,
   volitelně chráněné). Před přijetím InitPad u provideru ověří repozitář,
   SHA, běh, cestu workflow, událost, větev a to, že běh nepochází z forku.
   - **GitHub** používá OIDC token workflow (`id-token: write`) s audience
     InitPadu. InitPad ověří podpis a claims (`repository_id`, `workflow_ref`,
     `ref`, `sha`, `run_id`, `event_name`), takže repozitář nedrží žádný
     dlouhodobý deploy token.
   - **Gitea** dokud nenabídne OIDC pro Actions, používá dnešní per-repo
     token (hash v databázi) a stejné ověření běhu přes API. Gitea nepředává
     secrets workflow spuštěným z forku.
   - Artifact z neodpovídajícího workflow se odmítne a odmítnutí se zapíše.
     Preflight přestane hledat řetězce ve workflow; projekt po importu čeká
     na první ověřený handoff. Repozitáře bez vlastního CI dostanou
     vygenerovaný workflow.
   - Výsledek nasazení InitPad vrací zpět jako check run nebo commit status,
     takže je vidět i ve vlastním workflow a v pull requestech.

4. **Kontroly artifactu.** Při ingestion InitPad ověří digest každé image,
   limity velikosti a počtu vrstev a spustí sken zranitelností a tajných klíčů
   ve vrstvách. Nalezený klíč nebo kritická zranitelnost blokuje produkční
   žádost a v dev/test se zobrazí jako varování; policy mění owner. SBOM se
   ukládá k releasu.

5. **Release.** Release je neměnná sada právě jednoho artifactu pro každou
   službu manifestu, schválená podoba manifestu a commit SHA. `Environment`,
   `DeploymentOperation` a `ProductionDeploymentRequest` ukazují na release.
   Promotion dev → test → prod a rollback pracují s celým releasem. Existující
   artifacty se migrují na release s jednou službou.
   **Částečné buildy:** pokud CI postaví jen změněné služby, release převezme
   poslední ověřené artifacty ostatních služeb jen tehdy, když jejich commit
   je předkem commitu releasu na výchozí větvi a v cestách služby se mezi
   nimi nic nezměnilo (porovnání přes SCM API). Jinak release vyžaduje nový
   build služby.

6. **Runtime více služeb na Agentovi.**
   - Služby prostředí běží ve workspace síti allocation a navzájem se vidí
     přes DNS podle jména služby. Každý kontejner nese label
     `com.initpad.service`.
   - Dnešní hardening platí pro každou službu bez výjimky: `CapDrop: ALL`,
     `no-new-privileges`, limity paměti, CPU a PID, žádné mounty hostitele,
     zařízení ani Docker socket. Sdílené SaaS targety navíc vyžadují
     user namespace remapping nebo rootless Docker.
   - Agent spustí kandidáty všech služeb a gateway přepne, až když jsou
     healthy všichni. Jinak kandidáty odstraní a původní release běží dál.
     `worker` nemá port ani routu; health znamená běžící kontejner bez
     restartů po dobu ověření.
   - Gateway prostředí podporuje path routing pod jedním stabilním hostname
     (`/api` → `backend`, `/` → `frontend`).
   - Config vars dostanou volitelné pole `service`; tajná hodnota bez něj
     platí pro všechny služby. Hodnoty se nikdy nepředávají jako build
     argumenty.
   - **Runtime konfigurace pro statické frontendy:** manifest může označit
     veřejné (netajné) proměnné a cestu souboru. Agent soubor vygeneruje a
     zapíše do vytvořeného kontejneru před startem přes Docker archive API,
     bez mountu hostitele. Jedna image tak funguje ve všech prostředích.
   - Kvóty allocation se počítají za kontejnery, CPU, paměť a místo na
     volumes, ne za projekty.

7. **Úlohy a plány.** `jobs` jsou jednorázové kontejnery z image releasu.
   Úloha `release` (typicky migrace) proběhne před cutoverem; její selhání
   nasazení zastaví a původní release běží dál. `schedules` spouští Agent
   podle cronu jako jednorázové kontejnery se stejným hardeningem, limitem
   doby běhu a zákazem souběhu. Minimální interval určuje policy allocation.

8. **Spravované stavové služby.** Manifest může požádat o `postgres` nebo
   `redis` z allowlistu verzí, které spravuje platforma (image připnuté
   digestem, ne volbou uživatele). Každé prostředí má vlastní instanci a
   pojmenovaný volume vlastněný platformou. Credentials generuje InitPad a
   předá je jako tajné config vars jen službám, které je v manifestu
   deklarují. Zálohy jsou šifrované a ukládají se do úložiště platformy
   s retencí; obnova je explicitní operace ownera nebo admina a zapisuje se
   do auditu. Smazání prostředí volume ponechá po dobu retence, pokud owner
   výslovně nepožádá o okamžité smazání. Data se mezi prostředími nikdy
   nekopírují automaticky, zejména ne z produkce do dev.

9. **Domény a migrace projektů.**
   - Prostředí může mít více veřejných hostname. Vlastní doména se aktivuje
     až po ověření vlastnictví záznamem DNS TXT, aby nešlo převzít cizí
     doménu.
   - Převodník `docker-compose.yml` vytvoří návrh manifestu z bezpečné
     podmnožiny (služby, buildy, porty, proměnné, healthcheck, `depends_on`,
     databáze jako spravovaná služba) a vypíše odmítnuté volby s důvodem.
     Compose se nikdy nespouští.
   - Image z externí registry jsou ve výchozím stavu vypnuté. Owner je může
     povolit jen pro image připnuté digestem a podepsané (cosign) identitou,
     kterou určí policy workspace.

**Postup po obhajobě.**

1. Bezpečný handoff a kontrakt: manifest, schvalování změn, identita
   workflow, OIDC, kontroly artifactu.
2. Release a runtime více služeb: Release, Agent multi-container, path
   routing, workery, config vars podle služby, runtime konfigurace.
3. Úlohy, plány a částečné buildy.
4. Spravované stavové služby.
5. Domény, převodník compose a podepsané externí image.
6. Ověření na forku `team-1` a dalším projektu mimo šablony.

**Důsledky.**

- Import přijme monorepo i repozitář s vlastním workflow. Projekt přidá
  manifest a handoff krok; kód upraví jen tehdy, když zapéká konfiguraci
  prostředí při buildu nebo předává tajné klíče do image.
- Projekt dál nemůže získat oprávnění, která mu policy nedovolí; rozšíření
  v mezích policy vždy prochází schválením člověka.
- Repozitář na GitHubu přestane držet dlouhodobý deploy token.
- Přechod na Release zasahuje deploy, promotion, produkční žádosti, Agent
  joby, rollback i UI a vyžaduje datovou migraci a nové živé ověření
  cutoveru, fencingu a rollbacku.
- Spravované stavové služby dělají z Agenta správce dat: retence, zálohy,
  obnova a kapacita disku se stávají provozní odpovědností targetu.
- Health releasu je tak dobrý jako nejslabší služba; jedna vadná služba
  zablokuje nasazení ostatních.
- `THREAT_MODEL.md` se při implementaci doplní o identitu workflow, OIDC,
  schvalování manifestu a stavové služby.

**Testování.** Jednotkové testy validace manifestu (neznámé klíče, limity,
zakázané volby), výpočtu rozšíření oprávnění, ověření OIDC claims a identity
workflow (cizí cesta, událost `pull_request`, fork, jiná větev musí být
odmítnuty) a skládání releasu z částečných buildů včetně odmítnutí
artifactu mimo linii výchozí větve. Integrační testy promotion a rollbacku
releasu se dvěma službami, release úlohy a zálohy a obnovy Postgresu.
Živé ověření na Agent targetu: fork `team-1` s vlastním GitHub workflow
projde importem, schválením manifestu, dev deploy s migrací, promotion do
testu a produkční žádostí; selhání health jedné služby ponechá původní
release; artifact z workflow mimo povolenou identitu je odmítnut.
