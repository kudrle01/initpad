# ADR-130 — API exportuje traces a metriky přes explicitní OTLP hranici

**Kontext.** Strukturované logy a workflow correlation z ADR-101 umožňují
dohledat jednu operaci, ale bez traces a metrik nelze spolehlivě měřit latenci,
chybovost ani odlišit zdravé API repliky. Povinně přibalený collector by naopak
zavedl skrytou stavovou závislost do self-hosted instalace a sám by neřešil
retenci, přístupové role ani alerting.

**Rozhodnutí.** API má opt-in OpenTelemetry Node SDK. Po explicitním zapnutí
odesílá stabilní traces a metrics přes OTLP/HTTP na jediný validovaný privátní
collector. Každá replika nese service name, verzi a náhodný instance id.
Automatická instrumentace pokrývá runtime a podporované HTTP/framework/client
vrstvy; filesystem spans jsou vypnuté, health probe se netracují a úspěšné
se nezapisují do access logu. Vlastní request counter a histogram nepoužívají
raw URL ani tenant identity.

Aktivní trace id a span id se přidávají do stávajícího redigovaného JSON logu.
Logy zůstávají na stdout pro runtime collector; experimentální JavaScript
logs SDK není produkční podmínka. Self-hosted profil zůstává defaultně bez
exportu, SaaS profil vyžaduje privátní OTLP endpoint. Selhání collectoru nesmí
shodit aplikační readiness.

**Důsledky.** Backend lze zvolit a měnit mimo aplikaci a vendor credentials
zůstávají pouze v collectoru. Exportní hranice, nízká kardinalita, retenční
minimum, alert baseline a incident postup jsou dokumentované. Produkční gate
ale zůstává otevřený, dokud konkrétní staging backend neprokáže alerty, mazání
po retenci, role a telemetry-gap chování dvou API replik.

**Testování.** Jednotkové testy odmítají neúplný, credential-bearing nebo
neomezený endpoint, ověřují opt-in default a chrání trace pole logu před
podvržením message objektem. SaaS manifest test vyžaduje explicitní collector.
Živá staging acceptance je samostatný provozní důkaz.
