# ADR-139 — Šablonové CI testuje, staví a publikuje image v jednom jobu s cache vrstev v registry projektu

**Status:** Accepted

**Kontext.** Workflow šablon měla čtyři joby: `build`, `test`, `docker build`
a `deploy`. Každý job odpovídal jedné fázi pipeline v UI. Dokud všechny joby
sdílely jeden Docker daemon, druhý a třetí build stejného Dockerfilu vzal
vrstvy z prvního a vrstvy závislostí zůstávaly i mezi pushi. Sdílená cache ale
byla právě tou dírou mezi tenanty, kterou zavřel ADR-138. Od něj běží každý job
na vymazaném daemonu. Každý ze čtyř jobů si proto znovu načte job image a
`build`, `test` i `docker build` stavěly image od nuly. GitHub edice měla
stejný problém vždy, protože GitHub spouští každý job na nové VM.

**Rozhodnutí.**

1. Workflow šablony má jediný job `build` s kroky `test`, `build image`,
   u Laravel a Symfony `smoke-test image`, `publish image` a
   `notify platform`. Krok
   `test` staví stage Dockerfilu, ve kterém běží testy (`test`, u JS šablon
   `build`); `build image` pak ve stejném daemonu použije už postavené vrstvy.
   Callback na platformu je poslední krok s `if: always()` a posílá
   `ciStatus: ${{ job.status }}`.
2. Build bere a ukládá vrstvy v registry projektu:
   `--cache-from`/`--cache-to type=registry` s tagem `buildcache` vedle image
   projektu (šablony se samostatným stage `test` mají navíc
   `buildcache-test`), v režimu `mode=max`, takže cache
   pokrývá i mezistupně multi-stage buildu. `ignore-error=true` zajistí, že
   problém s cache build nezastaví. Zapisovat do ní umí jen CI s registry
   tokenem vlastníka repozitáře (ADR-134), takže tenanti cache nesdílejí a
   daemon může zůstat po každém jobu vymazaný.
3. CI daemon používá containerd image store
   (`--feature=containerd-snapshotter=true`), v instalaci i ve vývojovém
   stacku `infra/`. Jen s ním umí běžný `docker build` exportovat cache do
   registry bez samostatného BuildKit kontejneru; na daemonu bez něj workflow
   šablony skončí chybou `Cache export is not supported for the docker
   driver`. Pro lokální cache image daemon potřebuje i
   `--insecure-registry=172.31.250.10:5000`, protože containerd jinak
   zkouší HTTPS.
4. Buildy používají `--provenance=false` a runner nastavuje jobům
   `BUILDX_NO_DEFAULT_ATTESTATIONS=1`. S containerd image store by buildx
   jinak k image přidal atestaci provenance a pushnul index, který Gitea 1.22
   odmítne (`404`), a to i u workflow starších projektů. Do registry tak jde
   obyčejný Docker manifest jako dřív a platforma image převezme beze změny.
5. Pipeline v API ukazuje pro nové projekty fáze `build` a `publish`. Projekty
   vygenerované dřív, jejichž SCM hlásí joby `test`, `docker build` nebo
   `deploy`, si ponechají původní čtyři fáze. Publikace přejde na `running`,
   až když jsou všechny CI fáze před ní úspěšné.
6. GitHub edice dostane stejný jediný job. Převod workflow odstraní
   přihlášení do registry i cache a krok `publish image` nahradí uložením image
   jako Actions artefaktu (ADR-049). Callback čte ID a digest artefaktu z
   výstupů kroku `initpad-artifact`.

**Důsledky.** Push projde jedním načtením job image a jedním buildem místo
čtyř načtení a tří buildů. Neměněné vrstvy závislostí se stáhnou z registry
místo nového buildu. Neúspěšný test je v UI vidět jako neúspěšný `build`;
konkrétní krok ukáže log jobu. Stávající projekty mají dál svůj čtyřjobový
soubor a zrychlí se, až si stáhnou nové workflow z obrazovky importu a nahradí
jím `.gitea/workflows/ci.yml`. Registry projektu nese navíc jeden nebo dva
tagy cache, které smazání projektu odstraní spolu s image.

Balíčky v Gitee patří účtu, ne repozitáři (ADR-134). Člen týmu, který přečte
registry token repozitáře, proto může přepsat i cache jiného projektu téhož
vlastníka, stejně jako dnes může přepsat jeho image. Cache tedy nepřidává nové
riziko a úplně ho odstraní až Gitea organizace pro každý workspace. GitHub
edice cache vrstev nemá.

**Testování.** Živá zkouška s Gitea 1.22.6, `act_runner` 0.2.13 a službami z
`deploy/docker-compose.yml`, s workflow šablon a Dockerfilem se stejným
základním image:

- Workflow šablony Flask prošlo napoprvé za 123 s a uložilo tagy
  `buildcache` a `buildcache-test`. Další push na vymazaném daemonu krok
  závislostí nespustil, jen stáhl jeho vrstvu z registry, a job trval 83 s.
- Workflow šablony Next.js s testy v build stage trvalo 115 s a při dalším
  pushi 85 s. Vrstvu závislostí stáhlo z registry a testy kvůli změně zdroje
  spustilo znovu.
- Rozbitý test job zastavil a platforma dostala `ciStatus: failure`.
- Stejný projekt se starým čtyřjobovým workflow prošel také, jeho joby ale
  trvaly dohromady 371 s. Bez `BUILDX_NO_DEFAULT_ATTESTATIONS` jeho job
  `docker build` při pushi indexu do Gitea selhal.

Testy kontraktu šablon hlídají jeden job, cache, `--provenance=false` a
callback. Unit testy ověřují fáze nových i starších projektů a převod workflow
pro GitHub. Kontraktní test runneru hlídá containerd image store a vypnuté
výchozí atestace.
