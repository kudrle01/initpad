# ADR-172 — Pracovní soubory deploye API leží na disku

**Status:** Accepted

**Kontext.** Před deployem z Gitea registry API uloží testovaný image jako
`docker save` archiv (`project-registry-artifact-capture.ts`), spočítá jeho
digest a nahraje ho do object storage. Archiv vznikal v `os.tmpdir()`, tedy v
tmpfs `/tmp` o velikosti 256 MB. Image šablony Next.js má 541 MB, takže deploy
skončil chybou `ENOSPC: no space left on device, write`, přestože disk měl
desítky GB volných. Stejně dopadne každý větší image, například Spring Boot.
Zvětšit tmpfs nejde: jeho stránky se počítají do `mem_limit: 768m` kontejneru
API.

**Rozhodnutí.**

1. Self-hosted `docker-compose.yml` připojuje API pojmenovaný volume
   `api-work` na `/var/lib/initpad-work` a nastavuje `TMPDIR` na tuto cestu.
   Všechna místa, která v API volají `mkdtemp(tmpdir())`, tak pracují na disku
   bez změny kódu. tmpfs `/tmp` a read-only kořen zůstávají.
2. Volume na rozdíl od tmpfs přežije restart. API proto při startu, ještě než
   přijme práci, smaže v `os.tmpdir()` položky s prefixem `initpad-`, který
   používají všechny jeho dočasné adresáře (`common/work-dir.ts`).
3. `backup.sh` má zálohované volume vyjmenované, `api-work` mezi nimi není.

**Důsledky.** Deploy potřebuje volné místo na disku Dockeru zhruba ve velikosti
image, ne v paměti. SaaS profil `saas.compose.yml` má stejné omezení: artefakt
GitHub Actions s image archivem stahuje do tmpfs `/tmp` o velikosti 256 MB.
Tato změna ho neupravuje, protože SaaS se ověřuje na externím stagingu; úprava
tam má projít stejným postupem.

**Testování.** Živě na lokálním stacku: v kontejneru API se archiv image
`my-project-2` (527 MB) zapsal do `/var/lib/initpad-work` a po úklidu adresář
zůstal prázdný. Unit test hlídá, že úklid maže jen položky `initpad-*`,
kontraktní test hlídá `TMPDIR`, volume a jeho vynechání ze zálohy.
