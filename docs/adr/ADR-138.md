# ADR-138 — Každý CI job běží na čerstvě vymazaném Docker daemonu

**Status:** Accepted

**Kontext.** ADR-021 oddělil CI od hostu samostatným rootless DinD daemonem.
Tento daemon ale sdílely všechny joby všech workspaces a job dostává jeho API,
aby mohl stavět image. Cokoli job v daemonu nechal, použil další job jiného
workspace: běžící kontejner, volume, image pod běžným tagem (například
`node:20`), BuildKit cache nebo soubor v datovém adresáři daemonu, který job
přes Docker API připojí do vlastního kontejneru. Člen jednoho workspace tak
mohl změnit build cizího projektu a získat jeho registry a deploy token.
`force_pull` ani prázdné `valid_volumes` tomu nebrání, protože omezují jen to,
co připojí `act_runner`, ne to, co job udělá přes API. Při kapacitě větší než
1 navíc souběžné joby sdílely daemon současně. Vestavěný cache server
`act_runner` je jedno úložiště pro všechny repozitáře, takže job mohl obnovit
obsah, který uložil jiný projekt.

**Možnosti.** (a) Mezi joby mazat známé objekty (`prune`). Je to výčet toho, na
co se nezapomnělo: nepokryje soubory, které job zapíše do adresářů daemonu,
swarm ani pluginy. Kvůli bezpečnosti by stejně musel mazat image i build cache,
protože job je umí změnit přímo na disku, takže proti (b) nic neušetří.
(b) Před každým jobem daemon celý vymazat a po jobu ho restartovat.
(c) Samostatná VM nebo microVM (Kata, Firecracker) pro každý job. Přidává
hranici jádra, ale vyžaduje KVM na hostu, které mnoho VPS a cloudových VM
nenabízí, a nehodí se k instalaci jedním příkazem. Roadmapa microVM drží mimo
scope. SaaS edice tento runner nepoužívá vůbec, její CI běží na GitHub-hosted
runnerech.

**Rozhodnutí.** Varianta (b).

1. `act_runner` 0.2.13 přebírá s `daemon --once` jeden job. Vstupní skript
   `deploy/runner/ci-runner.sh` po jobu zapíše do volume `runner-reset` engine
   ID daemonu, který job použil, a další job spustí až na daemonu s jiným
   engine ID. Engine ID vzniká znovu při vymazání dat, job si ho nemůže zvolit
   a skript čte jen první pole odpovědi `/info`. Při vlastním startu skript
   nejprve vyžádá reset, protože předchozí job mohl přerušit restart runneru.
2. Vstupní skript `runner-docker` (`deploy/runner/ci-daemon.sh`) při každém
   startu smaže celý datový adresář daemonu. Soubory jobů patří podřízeným UID
   rootless user namespace, proto je maže uvnitř tohoto namespace. Když něco
   zůstane, daemon nespustí. Na požadavek o reset vlastní instance skript
   okamžitě skončí; init kontejneru ukončí všechny procesy jobu a restart policy
   kontejner spustí znovu. Kořenový souborový systém je jen pro čtení a
   zapisovatelné cesty (`/tmp`, `XDG_RUNTIME_DIR`, domovský adresář) jsou
   tmpfs, takže restart zahodí i soubory, které job zapsal přes bind mount,
   například konfiguraci daemonu v domovském adresáři. `runner-docker` volume
   `runner-reset` připojuje jen pro čtení.
3. `act_runner` s credentialem runneru zůstává v samostatném neprivilegovaném
   kontejneru. V kontejneru daemonu by si ho job přes bind mount přečetl a mohl
   by se vydávat za runner a přebírat joby jiných repozitářů. Proto nepoužíváme
   oficiální image `act_runner` s vestavěným DinD.
4. Bundled runner provádí právě jeden job. `INITPAD_RUNNER_CAPACITY` musí být
   1 a jiná hodnota instalaci zastaví s vysvětlením. Souběžné joby by
   potřebovaly více dvojic runner a daemon; to je samostatná budoucí práce.
5. Služba `runner-image-cache` (registry 3.0.0) je pull-through cache pro image
   z Docker Hubu. Daemon ji používá jako `--registry-mirror` na pevné adrese
   sítě `ci-control`. Cache odmítá push, mazání i zápis manifestu (`405
   UNSUPPORTED`) a nemá přihlašovací údaje k Docker Hubu, takže job do ní nic
   nevloží a dostane z ní jen veřejné image. Opakované stahování po resetu
   zůstává v lokální síti a pod limity Docker Hubu.
6. Cache server `act_runner` je vypnutý.

**Důsledky.** Žádný job nevidí kontejnery, volumes, image, build cache ani
soubory daemonu jiného jobu, a to ani jobu stejného projektu. Každý job si
znovu načte job image (asi 544 MB komprimovaně) z lokální cache; v sandboxu s
limitem 1 CPU to trvalo asi 80 s. Docker build začíná bez vrstev z předchozích
jobů, takže šablonová pipeline, která image staví ve třech jobech, trvá déle.
Zrychlí ji vyšší `INITPAD_RUNNER_CPU_LIMIT`. Strukturálně ji zrychlí build
jednou za pipeline nebo build cache v registry vlastního projektu; obojí mění
fáze pipeline v UI i převod workflow pro GitHub, a je proto samostatnou
budoucí prací. Instalace s kapacitou 2 a více musí upravit `deploy/.env`.
`actions/cache` nic neobnoví a job pokračuje bez cache. Vývojový stack v
`infra/` slouží jednomu vývojáři a sdílený daemon si ponechává; s instalací
sdílí jen konfiguraci runneru, takže i v něm je cache server vypnutý.

Vnější kontejner daemonu je dál privilegovaný (ADR-021). Únik z rootless user
namespace by se tak dostal do kontejneru daemonu, ne však ke credentialu
runneru. Síťový přístup jobů na gateway hostu se nemění. Cache roste až do
vypršení obsahu po 7 dnech. Registry 3.0.0 bez dostupného Docker Hubu při
startu spadne; restart policy start opakuje a daemon mezitím stahuje přímo z
Docker Hubu.

**Testování.** Živá zkouška s Gitea 1.22.6, `act_runner` 0.2.13 a Docker 27.5.1
nad službami z `deploy/docker-compose.yml`: první job vytvořil volume, kontejner
a stáhl image, druhý běžel na daemonu s jiným engine ID a nic z toho nenašel.
Soubory podřízených UID v adresáři s právy `0700` běžné `rm` nesmazalo, mazání v
user namespace odstranilo vše a daemon naběhl prázdný. Soubor zapsaný do
domovského adresáře restart nepřežil. Restart `act_runner` vynutil reset
daemonu. Reset trvá asi 3 s. Cache odmítla push, mazání i zápis manifestu a
po resetu obsloužila stažení image z lokálního úložiště. Kontraktní testy hlídají
konfiguraci služeb, vypnutý cache server a odmítnutí kapacity jiné než 1.
