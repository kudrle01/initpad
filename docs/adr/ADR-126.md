# ADR-126 — Process-bound deployment používá obnovovaný generační lease

**Kontext.** `Environment.activeOperationId` brání dvěma uživatelským akcím
současně měnit stejné prostředí, ale neprokazuje, který API proces právě provádí
provider operaci. Startup recovery proto mohl na jedné replice ukončit
deployment, který stále zdravě běžel na jiné, a pozdní worker mohl následně
publikovat zastaralý výsledek.

**Rozhodnutí.** Operation-backed deployment a start před provider prací
atomicky získá krátký lease na `DeploymentOperation`. Databázový čas určuje
expiraci, proces lease obnovuje během pomalé operace a každý takeover zvýší
`executionGeneration`. Phase, progress a terminal publication provedené
workerem jsou svázané s ownerem a generací. Recovery mění pouze prokazatelně
expirovanou nebo starou legacy operaci a její compare-and-set zahrnuje generaci.

Vnořená část stejné operace používá stejný execution kontext. Po předání
Agentu se process lease uvolní: další vlastnictví a fencing zajišťuje trvalý
`AgentJob` lease. Ztráta databázového lease je fail-closed; worker smí dokončit
lokální cleanup, ale nesmí publikovat úspěch ani selhání do trvalého stavu.

**Proč.** Tím se oddělí uživatelský environment lock od skutečného vlastnictví
externí práce. Generace blokuje ABA závod, pravidelné obnovení chrání dlouhé
deploye a CAS recovery nemůže přepsat právě převzatou operaci.

**Důsledky.** Více API replik smí bezpečně obsluhovat operation-backed deploy
bez falešného startup recovery. Toto rozhodnutí zatím nekryje samostatnou
artifact verification/ingestion ani synchronní direct stop/remove a target
mutation. Veřejný mutační SaaS proto zůstává single-replica do uzavření těchto
hranic.

**Testování.** Testy ověřují obnovu během pomalé provider práce, fenced terminal
publication, odmítnutí workeru po ztrátě lease, pasivní recovery živé operace,
CAS takeover a zachování trvalého Agent handoffu.
