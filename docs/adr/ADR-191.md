# ADR-191 — Prostředí s přímými porty má stálý port v proxy kontejneru

**Status:** Accepted

Upravuje [ADR-180](./ADR-180.md).

**Kontext.** V režimu přímých portů publikuje Agent port hostitele přímo na
kontejneru revize (ADR-180). Kandidát se ale vytváří a kontroluje, zatímco
stará revize svůj port ještě drží, a Docker nedovoluje přesunout publikovaný
port na běžící kontejner. Projekt proto při každém nasazení střídá dva porty.
V uživatelském testu 0.2.47 (nález N4, závažnost vysoká) respondent po nasazení
nového commitu obnovil stránku na staré adrese, nedostal odpověď a situace
působila jako pád aplikace, ačkoli aplikace běžela dál na novém portu.
V režimu spravované brány tento problém není, protože adresu drží brána.

**Možnosti.**
(a) Stálý port drží malý proxy kontejner prostředí. Revize publikují port jen
na loopback pro kontrolu zdraví a proxy posílá provoz na jméno kontejneru
aktivní revize v síti workloadu.
(b) Po kontrole zdraví starou revizi zastavit a kandidáta vytvořit znovu na
stálém portu. Je to jednodušší, ale každé nasazení má výpadek po dobu startu
aplikace.
(c) Doporučit pro všechny targety spravovanou bránu. Brána potřebuje DNS
záznamy a certifikáty, které menší instalace a studentské servery nemají.

**Rozhodnutí.** Varianta (a).

1. Ke každému workloadu v režimu přímých portů patří kontejner
   `<jméno workloadu>-proxy` v síti workloadu. Používá Caddy ve stejném
   připnutém obrazu jako brána v `apps/agent/install.sh`, proměnná
   `INITPAD_AGENT_DIRECT_PROXY_IMAGE` ho může nahradit jen obrazem připnutým
   digestem. Port hostitele dostane proxy z rozsahu ADR-180 a drží si ho
   labelem `com.initpad.host-port`, i když je zastavená.
2. Proxy nemá admin API ani perzistentní konfiguraci. Upstream je alias
   `initpad-active`, který má aktivní revize v síti prostředí. Jméno kontejneru
   použít nejde, protože může být delší než 63 znaků, které DNS dovoluje pro
   jednu část jména. Caddy alias překládá znovu každou sekundu (`dynamic a`)
   a krátce opakuje požadavky, které během přepnutí selžou.
   Kontejner běží s read-only rootfs, bez capabilities kromě
   `NET_BIND_SERVICE`, s `no-new-privileges` a s limity paměti, CPU a procesů.
3. Revize publikuje port jen na `127.0.0.1` s náhodným portem stejně jako
   ve spravované bráně. Slouží jen kontrole zdraví.
4. Při přepnutí se stará revize přejmenuje na `<jméno>-retiring-<revize>`
   a zdravý kandidát dostane jméno workloadu. Docker nastavuje alias jen při
   připojení do sítě, a proto Agent kandidáta ze sítě odpojí a připojí znovu
   s aliasem. Alias pak chvíli vrací obě revize. Po dvou sekundách, kdy už
   Caddy zná novou adresu, se stará revize zastaví s časem na dokončení
   požadavků a smaže. Alias zůstává v nastavení kontejneru i po restartu.
5. Výsledek jobu hlásí port proxy. API skládá URL prostředí z `hostPort`
   jako dosud, takže se nemění ani API, ani protokol.
6. Zastavení a spuštění prostředí zastaví a spustí revizi i proxy. Smazání
   prostředí nebo projektu smaže i proxy. Rollback je nasazení, a proto
   používá stejnou cestu.
7. Prostředí nasazené starším Agentem se převede při prvním nasazení novým
   Agentem. Proxy převezme port staré revize, aby adresa zůstala stejná, a to
   jednou za cenu krátkého výpadku mezi smazáním staré revize a startem proxy.
   Když port mezitím obsadí něco jiného, proxy dostane nový port z rozsahu.
8. Když se mezi revizemi změní port aplikace v kontejneru, Agent proxy na
   stejném portu hostitele vytvoří znovu. Krátký výpadek je v tom případě
   přijatelný, protože jde o výjimečnou změnu.

**Důsledky.** Adresa prostředí v režimu přímých portů přežije nasazení,
rollback, restart kontejneru i serveru. Nasazení zůstává bez výpadku a firewall
stačí otevřít pro stejný rozsah jako dosud. Každé prostředí má navíc jeden malý
kontejner a Agent musí umět stáhnout obraz proxy. Na serveru bez přístupu
k Docker Hubu je potřeba obraz nahrát předem, nebo nastavit
`INITPAD_AGENT_DIRECT_PROXY_IMAGE` na kopii v dostupném registru. Změna je jen
v Agentovi a vyžaduje jeho release 0.18. Starší Agent se chová podle ADR-180.

**Testování.** Unit testy v `apps/agent/src/docker-lifecycle.test.ts` s
podvrženým Docker API pokrývají první nasazení, opakované nasazení se stejným
portem, převod revize staršího Agenta, změnu portu aplikace, zastavení,
spuštění a smazání, selhání stažení obrazu proxy a opakování startu kandidáta
při obsazeném portu. Dne 22. listopadu 2026 proběhlo ověření v lokálním labu
s Agentem z této větve na produkčním prostředí s přímými porty. Převod revize
z Agenta 0.17 zachoval adresu a měl jednorázový výpadek asi 3 s. Při dalším
nasazení nové verze prošlo 132 dotazů během 27 s bez jediné chyby, adresa
i kontejner proxy zůstaly stejné. Alias přežil restart revize. Ověření odhalilo
dvě chyby první verze, které jsou opravené: proxy nepřeložila dlouhé jméno
kontejneru, a proto vznikl alias, a kandidát s náhodným portem neopakoval
start, když port držel proces mimo Docker. Na samostatném hostu a se
spravovanou bránou změna ověřená není.
