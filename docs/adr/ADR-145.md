# ADR-145 — Vstupy zvenčí mají ověřený tvar a podepsaný webhook se nepoužije dvakrát

**Status:** Accepted

**Kontext.** Audit z 9. října 2026 našel na hranicích API pět drobnějších
slabin:

- `GET /api/oauth/authorize` při neočekávané chybě vrátil prohlížeči text
  výjimky. OAuth parametry se četly bez kontroly typu, takže opakovaný parametr
  (`?client_id=a&client_id=b`) nebo vnořený objekt v těle tokenového požadavku
  skončil chybou 500. Basic autentizace klienta dělila údaje na každé dvojtečce.
- CI callbacky (`/api/ci/start`, `/api/ci/deploy`) a Gitea webhook měly tělo
  typované jako `interface`. Globální `ValidationPipe` takové tělo nekontroluje,
  takže do vyhledání projektu mohl dorazit objekt místo názvu repozitáře.
- Parametr `:env` v cestách projektů se nekontroloval.
- Web vkládal do `href` adresy, které nastavuje kdokoli s právem zápisu do
  repozitáře (cíl CI statusu), bez kontroly schématu. V produkci `javascript:`
  odkaz zastaví CSP, ve vývojovém režimu nic.
- GitHub podepisuje tělo webhooku bez časového razítka. Zachycené doručení tak
  platí navždy: přehrané staré `created` by obnovilo odinstalovanou GitHub App,
  přehrané `unsuspend` by zrušilo pozastavení.
- Gitea webhook o smazání repozitáře smazal projekt včetně produkce, aniž by
  ověřil, že repozitář opravdu neexistuje. Přehrané doručení nebo kdokoli se
  sdíleným webhook tokenem tak mohl smazat projekt s existujícím repozitářem.

**Rozhodnutí.**

1. OIDC endpointy berou každý známý parametr jako jeden řetězec. Opakovaný nebo
   vnořený parametr je `400 invalid_request`. Neočekávaná chyba vrátí jen
   `500 server_error`; podrobnosti jsou v logu. Basic credentials se dělí na
   první dvojtečce a dekódují podle RFC 6749 2.3.1.
2. CI callbacky a Gitea webhook čtou známá pole funkcí `stringFields`: pole
   musí být řetězec omezené délky, jinak `400`. Neznámá pole se dál ignorují,
   protože workflow už uložená v repozitářích, i upravená uživatelem, mohou
   posílat další hodnoty a striktní DTO by je rozbilo.
3. `EnvNamePipe` odmítne `:env` mimo `dev`, `test` a `prod` chybou `400`.
4. Web vytvoří odkaz z adresy, která nepochází z aplikace, jen když je to
   absolutní `http` nebo `https` adresa (`externalHref`). Platí to pro cíle CI
   statusů, adresy prostředí a odkazy na release.
5. GitHub webhook u událostí, které mění stav (`installation`,
   `installation_target`, `github_app_authorization`), vyžaduje hlavičku
   `X-GitHub-Delivery`. Po úspěšném zpracování uloží její ID do tabulky
   `GitHubWebhookDelivery`; doručení se známým ID potvrdí bez zpracování. Selhané
   doručení se neuloží, takže ho GitHub může doručit znovu se stejným ID. ID se
   uchovávají 90 dní a starší se mažou při dalším zápisu.
6. Gitea webhook o smazání repozitáře je jen podnět. Projekt se smaže, až Gitea
   na dotaz na repozitář odpoví 404, stejně jako při pravidelné rekonciliaci.
   Výpadek Gitey nic nesmaže; projekt odstraní pozdější rekonciliace.

**Důsledky.** Chybný tvar vstupu skončí srozumitelnou chybou 400 místo 500 nebo
nečekaného filtru v databázovém dotazu. Přehrání zachyceného GitHub webhooku do
90 dní nezmění stav instalace ani GitHub autorizace. Starší doručení by prošlo
znovu; GitHub ruční redelivery umožňuje jen několik dní, takže jde o
doručení, které útočník musel zachytit a déle než 90 dní uchovat. Gitea webhook
ID doručení neukládá: jediná akce, kterou spouští, nově ověřuje skutečný stav
repozitáře, takže přehrání ani podvržení nemá účinek.

**Testování.** Unit testy pokrývají opakované a vnořené OAuth parametry,
odpověď 500 bez textu výjimky, Basic credentials s dvojtečkou v secretu,
odmítnutí objektu v CI callbacku i v Gitea webhooku při zachování neznámých
polí, `EnvNamePipe`, odmítnutí `javascript:`, `data:` a relativních adres v
odkazech, jedno zpracování přehraného doručení, opakovatelnost selhaného
doručení, mazání starých ID a to, že webhook o smazání repozitáře projekt
nesmaže, dokud Gitea repozitář nehlásí jako neexistující. Migrace prošla nad PostgreSQL 16, Prisma po ní
nehlásí rozdíl schématu a opakovaný zápis stejného ID nic nepřidal.
