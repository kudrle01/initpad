# ADR-161 — Instalátor nastaví síť z jedné odpovědi a rozdá vlastní CA

**Status:** Accepted

Doplňuje [ADR-062](./ADR-062.md).

**Kontext.** Serverová instalace vyžadovala ruční úpravu pěti až osmi adres
v `deploy/.env`: veřejné URL platformy a Gitey, `INITPAD_DOMAIN`,
`INITPAD_GIT_DOMAIN`, registry pro Docker démon hostu a pro CI a režim TLS.
README režim `tls internal` pro interní síť vůbec neuvádělo, i když jde
o typický školní a firemní případ (jména na řadiči domény, server bez
veřejné dostupnosti).

S `tls internal` navíc instalace nefungovala celá. Certifikát vydaný lokální
CA Caddy neznal Docker démon hostu (pull z registry), izolovaný CI démon
(push do registry) ani throwaway image CI jobů, které klonovaly přes
veřejnou URL Gitey. Kořenový certifikát šlo získat jen přes
`docker compose exec` z volume Caddy.

Zvažované možnosti:

- Jen doplnit dokumentaci. Odmítnuto, ruční nastavení dělených adres je
  hlavní zdroj chyb a CI by s vlastní CA dál nefungovalo.
- Vložit CA do systémového úložiště hostu a do job image. Odmítnuto,
  změna systémové důvěry je širší, než je potřeba, a job image se stahují
  a mažou pro každý job (ADR-138).
- Vypnout ověření TLS (`insecure-registry`) pro jméno Gitu. Odmítnuto,
  registry pak není chráněná proti podvržení v LAN.
- Průvodce v instalátoru, důvěra omezená na jméno registry a interní
  checkout. Zvoleno.

**Rozhodnutí.**

1. `install.sh` se při prvním spuštění v terminálu zeptá na režim sítě:
   jen tento počítač, interní síť s DNS (`tls internal`), nebo veřejná
   doména (Let's Encrypt). U serverových režimů se ptá na jméno platformy a
   Gitu (výchozí `git.<nadřazená doména>`). Stejné hodnoty přijímá
   z parametrů `--local`, `--domain`, `--git-domain` a `--tls`. Z odpovědi
   vyplní všechny adresy v `.env` najednou. Další spuštění konfiguraci sítě
   nemění, změnu provede `--reconfigure`. Bez terminálu a bez parametrů
   zůstává lokální instalace jako dosud.
2. V režimu `tls internal` instalátor po startu Caddy exportuje **jen
   veřejný kořenový certifikát** do `.runtime/tls/initpad-root-ca.crt` a
   vypíše jeho otisk SHA-256. Privátní klíč CA volume Caddy neopouští.
3. Docker démon hostu důvěřuje CA jen pro jméno Gitu
   (`/etc/docker/certs.d/<git>/ca.crt`, případně uživatelský adresář
   rootless démona). Zápis může vyžádat `sudo`; systémové úložiště
   certifikátů instalátor nemění.
4. Izolovaný CI démon dostává adresář s veřejným certifikátem jen pro čtení
   a při každém startu jej zkopíruje do své konfigurace pro
   `INITPAD_CI_REGISTRY_HOST`. Checkout v CI jobech jde přes interní
   `http://host.docker.internal:<port>`, takže job image certifikát
   nepotřebují. Starší instalace s `tls internal` a veřejnou URL pro
   runner instalátor na tuto adresu převede a runner znovu zaregistruje.
5. Caddy nabízí certifikát na `/initpad-ca.crt` přes HTTP i HTTPS jména
   platformy. HTTP slouží pro stažení, dokud klient CA nezná; ostatní HTTP
   požadavky přesměrovává na HTTPS. Rewrite míří na jediný soubor, takže
   klíč v témže adresáři není dostupný.

6. API čte exportovaný certifikát (připojený jen pro čtení) při každém
   dotazu na metadata Agenta a vrací jeho cestu, otisk SHA-256 a jméno
   registry; soubor s privátním klíčem odmítne. **Manage Agent** pak
   v instalačním příkazu certifikát stáhne přes HTTP, ověří otisk, uloží jej
   do Docker `certs.d` pro registry a do `/etc/initpad-agent/ca.crt`,
   stáhne instalátor s `--cacert` a předá Agentovi `--ca-file`. Otisk
   pochází z HTTPS relace administrátora, takže podvržený certifikát
   příkaz zastaví. Systémové úložiště cílového serveru se nemění.

**Důsledky.**

- Interní síť stačí nastavit DNS záznamy na řadiči domény a odpovědět na
  dvě otázky. Klientům se certifikát rozdá přes GPO nebo stažením.
- Certifikát stažený přes HTTP lze v LAN podvrhnout; uživatel proto má
  porovnat otisk vypsaný instalátorem. GPO tento krok nepotřebuje.
- Agent servery dostanou certifikát z příkazu v **Manage Agent** (bod 6).
- Smazání volume `caddy-data` vytvoří novou CA, kterou je nutné znovu
  rozdat klientům i Agent serverům.

**Testování.** Caddyfile ověřen v připnutém image Caddy pro oba režimy:
stažení certifikátu přes HTTP s typem `application/x-x509-ca-cert`,
přesměrování ostatních cest, nedostupnost klíče a ověření HTTPS obou jmen
staženým certifikátem. Síťová část instalátoru ověřena nad kopií
`.env.example` pro parametry, chybné vstupy, průvodce v terminálu,
`--reconfigure` a opakované spuštění. Rootless CI démon s exportovaným
certifikátem pushne do registry za Caddy s `tls internal`, bez něj selže na
`x509`. Jednotkové testy pokrývají metadata CA v API a skládání příkazu
Agenta. Celá instalace v režimu
`tls internal` včetně CI buildu a deploye zatím neprošla.
