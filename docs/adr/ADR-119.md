# ADR-119 — Agent release prochází odděleným candidate a stable kanálem

**Kontext.** Podepsaný multiarch image, checksumy a Sigstore identita dokazují
původ a neměnnost vydání, ale samy nedokazují, že Agent správně přežije
reálný reboot, výměnu vlastního kontejneru nebo změnu control-plane URL.
Původní workflow vytvořilo z každého tagu rovnou stabilní GitHub release.
Produkční katalog jej tak mohl nabídnout dříve, než skončil clean-host
acceptance gate.

**Rozhodnutí.** Workflow `agent-v*` publikuje podepsaný release nejprve jako
GitHub prerelease. Běžný control plane používá
`INITPAD_AGENT_UPDATE_CHANNEL=stable` a prerelease ignoruje. Pouze disposable
testovací instalace smí explicitně zvolit `candidate`; web tento stav označí
přímo u nabízené aktualizace. Oba kanály stále vyžadují přesnou workflow
identitu podpisu, immutable OCI digest a ruční potvrzení ownerem nebo adminem
pro konkrétní target.

Po úspěšném acceptance se existující GitHub release povýší z prerelease na
stable. Image, manifest, podpisy, tag ani source commit se znovu nevytvářejí.
Odmítnutý kandidát zůstane prerelease a stabilní instalace jej nikdy neuvidí.
Verzovaný `deploy/agent-release.env` se aktualizuje až po povýšení a slouží
jen jako bootstrap pro nové servery nebo ruční recovery. Běžící Agenty
zjišťují pozdější stable verze z ověřeného katalogu, takže provozovatel
nemění `.env` při každém vydání.

**Proč.** Oddělení distribuce od provozního schválení zachovává jediný
auditovatelný artifact a současně brání tomu, aby se neotestovaný runtime stal
produkční nabídkou. Rebuild po acceptance by vytvořil jiný digest, který
acceptance nikdy neviděla. Automatický fleet rollout by zase odstranil
postupné nasazení a explicitní odpovědnost správce.

**Důsledky.** Release správce musí po testu provést explicitní promotion a
stabilní anonymní audit. Candidate control plane je záměrně odlišná provozní
konfigurace a nesmí obsluhovat produkční targety. GitHub release metadata je
jediný měněný stav; bezpečnostně rozhodující artifacty zůstávají neměnné.

**Testování.** API testy dokazují, že stable kanál novější prerelease
přeskočí a candidate kanál jej vybere a ověří. Webový test vyžaduje
viditelné označení candidate nabídky. Veřejný release audit prerelease ve
výchozím režimu odmítne a přijme jej jen s explicitním
`--allow-prerelease`. Repository gate hlídá, že Agent workflow kandidáta
nevydá rovnou jako stable.
