# ADR-158 — Staging vynucuje egress podle portů a alertuje z vlastního collectoru

**Status:** Accepted

**Kontext.** ADR-132 určil, že default-deny egress se vynucuje na hostu a že
observability vede přes OpenTelemetry Collector do Grafana Cloud. Staging kit
ale neobsahoval ani pravidla firewallu, ani sběr JSON logů kontejnerů, ani
alerty. Dva alerty z `docs/OBSERVABILITY.md` navíc stojí na událostech, které
API buď nelogovalo vůbec (převzetí role leadera), nebo jen jako řádek logu
(`mail.outbox.failed`), takže je metrický backend neviděl.

Zvažované možnosti pro egress:

- Allow-list podle doménových jmen přes forward proxy. Odmítnuto. Node API by
  muselo všechna odchozí volání posílat přes proxy, což mění kód kvůli jedné
  sestavě, a proxy by se stala další stavovou službou.
- Allow-list podle IP adres závislostí. Odmítnuto. GitHub, Cloudflare R2,
  Supabase i Grafana Cloud sedí za CDN, jejichž adresy se mění bez ohlášení.
- Allow-list podle cílových portů se zákazem privátních, link-local a
  metadata rozsahů. Zvoleno.

Zvažované možnosti pro logy a alerty:

- Grafana Alloy nebo jiný agent s Docker socketem. Odmítnuto, socket je
  ekvivalent roota na hostu a staging kit jej záměrně nepoužívá.
- Log alerty přímo v Loki. Odmítnuto pro dva alerty z šesti, protože by
  pravidla žila ve dvou backendech s různým jazykem dotazů.
- Collector čte soubory `json-file` driveru, filtruje je podle Compose labelů
  a počítá vybrané události do metriky. Zvoleno.

**Rozhodnutí.**

1. `deploy/staging/egress-firewall.sh` instaluje do `DOCKER-USER` a `OUTPUT`
   vlastní řetězce pro rozhraní výchozí trasy. Kontejnery smějí navázat nové
   spojení jen na TCP porty 443, 587, 5432 a 6543 a na DNS resolvery
   poskytovatele. Host navíc smí na NTP, port tunelu 7844 a porty 80 a 443.
   Privátní, link-local, CGNAT a metadata rozsahy jsou odmítnuté vždy.
   Systemd unit pravidla obnoví po startu i po restartu Dockeru.
2. Docker daemon připojuje ke každému řádku logu labely Compose projektu a
   služby. Collector čte `/var/lib/docker/containers` pouze pro čtení jako uid 0
   bez capabilities, zahodí řádky jiných projektů než `initpad-saas`, JSON
   záznamy API rozloží na atributy a logy odesílá přes OTLP.
3. Collector počítá události `mail.outbox.failed` a
   `control_plane.leader.acquired` do metriky `initpad.log.events`. API nově
   loguje `control_plane.leader.acquired` při každém převzetí lease
   `projects-lifecycle`.
4. Collector každých 30 sekund volá readiness veřejného originu přes edge.
   Zastavený collector proto nevyvolá `InitPadApiUnavailable`, jen
   `InitPadTelemetryGap`.
5. Všech šest alertů je jeden soubor `deploy/staging/alert-rules.yaml` ve
   formátu Prometheus pravidel s jednotkovými testy pro `promtool`.
6. `deploy/staging/edge-check.sh` z počítače provozovatele dokládá odpověď přes
   edge, zavřené porty originu, limit těla požadavku a blokaci dávky pravidlem
   rate limitingu na edge.

**Důsledky.** Kompromitovaný kontejner stále může posílat data na libovolnou
veřejnou adresu přes port 443; pravidla brání pohybu do privátních sítí,
metadata služby a jiným protokolům, nikoli exfiltraci přes HTTPS. Jde o další
vědomou odchylku od provozního minima ADR-132. Alert na výpadek jedné instance
se ozve i po každém plánovaném restartu, protože nová replika má nové ID
instance. Počítání událostí z logů závisí na tom, že collector běží; jeho
výpadek pokrývá alert na mezeru v telemetrii.

**Testování.** Konfiguraci collectoru validuje připnutý obraz a funkční test s
druhým collectorem jako backendem ověřil filtr projektů, rozklad JSON záznamů
a počty událostí. Pravidla alertů prošla `promtool check rules` a
`promtool test rules` nad `deploy/staging/alert-rules.test.yaml`. Firewall
prošel `apply`, opakovaným `apply`, sondami a `remove` v izolovaném síťovém
namespace. Kontraktní test v `scripts/saas-staging-kit.test.mjs` hlídá shodu
alertů, metrik a událostí s kódem a dokumentací. Živé ověření na stagingu
zůstává otevřené v roadmapě.
