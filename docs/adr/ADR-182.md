# ADR-182 — Aktualizace platformy se sladí se Supervisorem a nehlásí nepravdivý rollback

**Status:** Accepted

**Kontext.** Audit z 13. 11. 2026 (P0.3, P0.4) našel několik míst, kde se
aktualizace platformy mohla trvale zaseknout nebo hlásit nepravdivý stav:

- API při startu sekvenčně měnilo heslo v Gitee pro každý účet. Readiness
  pak trvala minuty a Supervisor (čeká ~120 s) aktualizaci vrátil až po
  migracích.
- Řádek `PlatformUpdateOperation` ve stavu `requesting`, `accepted` nebo
  `running`, o kterém Supervisor nevěděl, neměl expiraci a blokoval další
  aktualizace.
- `/v1/update` mělo 8s timeout, ale Supervisor před odpovědí ověřuje Sigstore
  bundle až 8 s. API pak hlásilo selhání aktualizace, která ve skutečnosti
  běžela.
- Rollback zapsal `rolled-back` ještě před obnovou a chyby (`copyFile` EPERM,
  selhání Compose) spolkl. Potom smazal předchozí descriptor.
- `update.lock` zůstal po `recovery-failed` a každá další aktualizace skončila
  hláškou „Another platform update is already running“.
- Když helper zemřel bez restartu Supervisoru, operace zůstala aktivní navždy.

**Rozhodnutí.**

1. Zpevnění hesel v Gitee běží na pozadí pod control-plane lease
   `gitea-password-hardening` a jen pro účty bez nového sloupce
   `User.giteaPasswordHardenedAt`. Nové účty ho dostanou při založení. Účet,
   u kterého volání selže, zůstane neoznačený a další průchod (za 10 minut
   nebo po restartu) ho zkusí znovu.
2. API slaďuje své řádky při každém čtení stavu a před novým požadavkem.
   Aktivní řádek, který Supervisor nezná, skončí jako `failed`/`interrupted`.
   Řádek `requesting` skončí po 5 minutách jako `failed`/`request-timeout`.
3. `/v1/update` má timeout alespoň 60 s. Request selže jen tehdy, když ho
   Supervisor výslovně odmítne (`SupervisorRejectedError`). Při timeoutu nebo
   přerušeném spojení řádek zůstane ve stavu `requesting` a bod 2 ho sladí.
4. Supervisor obnoví předchozí descriptor přejmenováním (`rename`). Zálohu
   descriptoru vytvoří zápisem nového souboru, ne přes `copyFile`. Stav
   `rolled-back` zapíše až po úspěšném `compose up` a health checku API, webu
   i Supervisoru. Jinak zapíše `failed`/`recovery-failed` se zprávou, která
   odkazuje na `initpad-install-release.sh` / `restore.sh` a uvádí cestu
   k záloze. Předchozí descriptor se v takovém případě nesmaže. Selhání před
   přepnutím images je `failed`, ne `rolled-back`.
5. `update.lock` obsahuje id operace. Zámek jiné operace je zastaralý a helper
   ho odstraní. Zámek se uvolní i ve stavu `recovery-failed`.
6. `GET /v1/status` u aktivní operace nejvýš jednou za 10 s spustí
   jednorázový recovery helper. Ten nic nedělá, dokud běží update nebo
   recovery helper.

Stavy zůstávají ve stávajícím schématu (`failed` + `stage`), takže starší API
a Supervisor si odpovědi dál rozumějí.

**Důsledky.** Start API nečeká na Giteu. Uvízlou aktualizaci vyřeší první
čtení stavu se Supervisorem online. Administrátor nikdy neuvidí „vráceno
zpět“, když stará verze neběží, a dostane konkrétní postup.

**Testování.** Jest pokrývá zpevnění hesel na pozadí (lease, opakování) a
slaďování řádků a timeoutu. node:test v Supervisoru pokrývá rename rollback,
`recovery-failed` při selhání Compose i health checku, zastaralý a vlastní
zámek a spuštění recovery ze stavu.
