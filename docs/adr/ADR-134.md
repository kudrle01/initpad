# ADR-134 — Gitea tokeny mají rozsah podle spotřebitele a CI dostává jen token pro registry

**Status:** Accepted

**Kontext.** Self-hosted edice vydávala uživateli při registraci a při každém
importu jediný Gitea token s oprávněním k zápisu do repozitářů, balíčků,
uživatele i organizací. Stejný token se ukládal jako Actions secret
`INITPAD_REGISTRY_PASSWORD` do každého repozitáře, který uživatel vlastnil,
včetně týmových projektů. Člen týmu s právem zápisu proto mohl upravit workflow,
secret vypsat a získat zápis do všech repozitářů autora, i v jiných
workspaces, a změnit jeho účet. Každé vydání navíc vytvořilo nový token s
názvem `initpad-platform-<čas>` a starý nikdy nezrušilo, takže jednou uniklý
token platil navždy. Reset hesla token neměnil.

Gitea 1.22 spravuje tokeny jen přes Basic autentizaci vlastníka účtu; admin
token ani `Sudo` nestačí. Název tokenu je v rámci účtu unikátní. Živá zkouška
na Gitea 1.22.6 potvrdila, že token s rozsahem `write:package` zvládne
`docker login` a `push` do registry vlastního účtu, ale nepřečte repozitář,
neklonuje, nezmění nastavení účtu a nepushne do registry jiného uživatele.
Token s rozsahem `write:repository` umí clone i push, ale nemění účet ani
organizace.

**Rozhodnutí.**

1. Token je určen spotřebiteli a má pevný název. Nové vydání token se stejným
   názvem nejprve smaže, takže předchozí kopie přestane platit.
   - `initpad-git` (`write:repository`) je Git token uživatele. Platforma ho
     ukládá šifrovaně a vrací ho jen přihlášenému vlastníkovi přes
     `GET /api/me/git-access` s `Cache-Control: no-store`.
   - `initpad-registry-<id repozitáře>` (`write:package`) je jediný credential,
     který dostává CI repozitáře jako `INITPAD_REGISTRY_PASSWORD`.
2. Platforma pro operace s tokeny nastaví účtu náhodné dočasné heslo, provede
   operaci a heslo hned znovu znáhodní, i když operace selže. Operace jednoho
   účtu se provádějí postupně, aby si souběžné požadavky dočasné heslo
   nepřepsaly.
3. Registry token se zruší spolu se secrety při odpojení repozitáře, při
   kompenzaci neúspěšného importu a při smazání repozitáře.
4. Registry tokeny repozitářů workspace se vymění, když člen ztratí právo
   zápisu, tedy při odebrání z workspace nebo snížení role na `viewer`. Kopie,
   kterou si mohl předtím přečíst, tím přestane platit. Selhání výměny se
   zaloguje a změnu členství nevrací.
5. Reset hesla uživatelem i administrátorem a deaktivace účtu nejprve zruší
   Git token. Když to Gitea nepotvrdí, reset skončí chybou a odkaz zůstane
   nevyužitý; administrátorský reset i deaktivace se neprovedou. Nový Git
   token se vydá při dalším otevření nastavení Git přístupu.
6. Existující instalace převede údržba vedoucí repliky. Pro každý účet nejprve
   vymění registry secret ve všech jeho repozitářích, teprve potom vydá nový
   Git token, zruší všechny tokeny `initpad-platform-*` a nastaví
   `User.giteaCredentialsScopedAt`. Převod běží vedle minutové údržby po
   dávkách 25 účtů, takže nezdrží start API, health gate aktualizace ani
   úklid prostředí. Neúspěch se opakuje v další dávce a žádné CI nezůstane s
   neplatným tokenem. Tento krok zároveň přebírá dřívější migraci projektů
   bez repozitářového CI tokenu.

**Důsledky.** Člen týmu, který přečte secrety repozitáře, získá jen možnost
publikovat a mazat container balíčky vlastníka repozitáře. Nezíská kód, účet
ani přístup k jiným repozitářům. Balíčky v Gitee patří účtu, nikoli
repozitáři, takže registry token stále dovoluje přepsat image jiného projektu
téhož vlastníka. Úplné oddělení vyžaduje převést týmové repozitáře do Gitea
organizace pro každý workspace. To zároveň vyřeší, že odebraný člen dál
vlastní repozitáře, které v týmu založil. Je to samostatná budoucí práce.

Běžná změna hesla Git token nemění, protože ji uživatel provádí se znalostí
současného hesla. Uživatel po resetu hesla nebo po migraci musí v Git klientovi
použít nový token z nastavení. GitHub edice se nemění, její CI používá
krátkodobý token GitHub Actions a artefakt místo registry secretu.

**Testování.** Unit testy nad simulací Gitea API ověřují rozsahy a názvy
tokenů, výměnu s neplatností předchozí kopie, sériové zpracování operací
jednoho účtu, znáhodnění hesla po chybě, rušení jen legacy tokenů, revokaci
při smazání repozitáře, pořadí migrace i opakování po chybě, rotaci při
odebrání člena a revokaci při resetu hesla a deaktivaci. Živá zkouška proti
Gitea 1.22.6 prošla stejným tokem včetně skutečného `docker push` s registry
tokenem.
