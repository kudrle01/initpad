# ADR-125 — Background lifecycle volí jediného leadera databázovým lease

**Kontext.** Každá API replika při startu spouštěla project reconciliation,
artifact retention a periodickou expiraci prostředí. Jednotlivé destruktivní
přechody sice používají databázový compare-and-set, ale nová replika mohla
startup recovery zaměnit živou operaci jiného procesu za přerušenou.

**Rozhodnutí.** Project lifecycle získává pojmenovaný `ControlPlaneLease`
atomickým PostgreSQL `INSERT ... ON CONFLICT ... WHERE`. O expiraci rozhoduje
databázový čas, ne hodiny kontejneru. Stejný owner lease obnovuje bez změny
generace; jiný proces jej smí převzít pouze po expiraci a generaci zvýší.

Pouze leader spouští startup reconciliation, retention a environment expiry.
Jednorázové recovery kroky provede právě při nové generaci, zatímco expiry běží
v každém leader cyklu. Lease se obnovuje i během dlouhého recovery. Při
shutdownu se záměrně nemaže; nástupce musí počkat na poslední prokázanou
expiraci, aby se dva workery nepřekryli.

**Proč.** Databázový řádek funguje se stávajícím PostgreSQL a nevyžaduje
Redis, Kubernetes Lease ani dlouhodobě rezervované DB spojení jako advisory
lock. Generace odliší běžné obnovení od skutečného failoveru.

**Důsledky.** Follower API replika může obsluhovat bezpečné read cesty, ale
background údržbu nespustí. Failover je omezený TTL lease, dnes nejvýše tři
minuty. Process-bound deployment doplňuje ADR-126; artifact ingestion a další
synchronní mutace stále potřebují vlastní execution lease a fencing před
active-active mutačním provozem.

**Testování.** Testy ověřují atomický claim, odmítnutí cizího živého ownera,
omezený vstup, pasivní follower, takeover nové generace, zákaz souběhu sweepu a
obnovu lease během pomalého startup recovery.
